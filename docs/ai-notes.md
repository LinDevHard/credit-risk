# Где ИИ ошибался и что исправлено

Работа велась с Claude Code. Ниже — места, где первый вариант был неверным или рискованным, и что с этим сделано.

1. **Доли в семантической модели через `avg`.** Первое, что приходит в голову агенту, — сделать PAR30 как `avg` по булевому флагу. Но это доля по **числу** кредитов, а по определению нужна доля по **сумме**. Исправление: в витрину добавлены колонки `par30_kzt`, `par90_kzt`, `npl_kzt`, а доля считается как отношение двух `sum`-мер. Тест сверяет её с эталоном.
2. **Списанные кредиты как «необратимое» состояние.** Сначала агент считал, что `written_off` монотонен. Запрос миграции между срезами показал 23 кредита, которые вернулись из списания. Метрики считаются строго по флагу на дату среза (как в определении), а аномалия вынесена в выводы для комитета.
3. **Подозрительно хорошая динамика.** Агент сначала описал снижение NPL как улучшение качества. Матрица миграции просрочки показала 53 кредита, перешедших из 90+ в 0 дней за месяц, поэтому вывод переформулирован: улучшение требует подтверждения.
4. **Мелочи окружения.** `launch.json` для превью дашборда сначала лёг не в ту папку. В тестах файлы открывались без закрытия (ResourceWarning) — заменено на `read_text()`.

Что агент сделал правильно с первого раза и что проверено тестами: дедупликация, курс строго на дату среза (31.08 ≠ 01.09), приоритет NPL в провизиях, концентрация по `group_id`, а не по `borrower_id`.

## Мои ручные проверки

- Запросом к `raw.portfolio` убедился, что в каждом срезе 2030 строк на 2000 уникальных `loan_id`, то есть по 30 дублей.
- По `reporting.v_data_quality` сверил очистку: 2030 − 30 − 25 = 1975 на 01.09 и 2030 − 30 − 8 = 1992 на 01.10. Это совпадает с README и с тестами.
